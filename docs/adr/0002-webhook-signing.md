# ADR-0002: Signing outbound webhooks

| | |
|---|---|
| Status | **Accepted** |
| Date | 2026-11-09 |
| Deciders | project owner (plan default), implemented by an agent |
| Supersedes | the "webhook signing (0.4)" line of `docs/plans/01-backend.md` §19 |
| Amended | 2026-11-09: secret rotation with a 24-hour overlap (see Decision) |

## Context

Release 0.4 lets an organization administrator register HTTPS endpoints that receive events (`payment.recorded`, `ticket.created`, ...) as JSON POSTs. The receiver must be able to tell that a request came from this OpenBekci instance, that its body was not changed, and that it is not an old request replayed by someone who recorded it. Receivers are small scripts in Go, Node, Python, shell or a home-automation hub: whatever we choose has to be verifiable with a standard library and a dozen lines.

Constraints from the plans: deliveries ride the River outbox (backend §11, one job per event and endpoint); the payload carries ids only, never records (so a leaked or mis-routed delivery discloses little, and the receiver reads the API with its own scoped key); the secret is state that must be stored encrypted (backend §16, `ENCRYPTION_KEY`); the server must not be usable to probe the internal network (SSRF).

## Options considered

| | Shared-secret HMAC-SHA256 over `timestamp.body` | Asymmetric signature (Ed25519), one key pair per instance or endpoint | mTLS to the receiver | Bearer token header only |
|---|---|---|---|---|
| Receiver effort | A hash function and a constant-time compare | A public-key library and key distribution (a public key per instance, fetched or pasted) | Client certificate management on every receiver | One string compare |
| Authenticity and integrity | Yes, for whoever holds the secret | Yes, and the receiver cannot forge | Yes, at the connection, not per message | Authenticity only, no integrity; a replayed request is accepted forever |
| Replay protection | Timestamp inside the signed string, tolerance window | Same, if the timestamp is signed | None per message | None |
| Secret exposure on our side | The secret must be readable by the server (sealed in the database) | Private key readable by the server, public key can be published | Private key and CA | Token readable by the server |
| Fit for LAN receivers and hobby scripts | Excellent | Needs libraries many shells lack | Poor | Excellent but weak |

A token alone gives no integrity and no replay protection. mTLS makes every receiver run a PKI. Ed25519 is attractive (receivers could not forge us) but forgery by the receiver is not a threat here: the receiver is the party the administrator chose to trust with the data. The cost, a public-key library and key distribution on every receiver, is what makes integrations fail in practice.

## Decision

**HMAC-SHA256 with a per-endpoint shared secret, over the timestamp and the exact body.**

- Every endpoint has its own secret, `whsec_` followed by 256 random bits in base64url, generated by the server and shown **once**, in the response that creates the endpoint. It is stored sealed with AES-256-GCM (`ENCRYPTION_KEY`, purpose `integrations.webhook_secret`, the organization and endpoint ids as additional authenticated data), never returned again and never written to the audit trail or logs. There is no endpoint to read it back. To change it, `POST /webhook-endpoints/{id}:rotate-secret` returns a new secret once and keeps the replaced one, sealed the same way, as a second signing secret for **24 hours** (`secret_previous_sealed`, `secret_previous_expires_at`). Deliveries in that window carry both signatures, newest first. A second rotation inside the window replaces the overlap; only one previous secret is kept.
- Each request carries
  - `OpenBekci-Signature: t=<unix seconds>,v1=<lower-case hex HMAC-SHA256(secret, t + "." + body)>`, where the key is the whole secret string (including `whsec_`) as UTF-8 and `body` is the raw request body bytes;
  - `OpenBekci-Delivery-Id`: the delivery's UUID, identical on every retry, for the receiver's own de-duplication;
  - `OpenBekci-Event`: the event type, for routing before parsing the body.
- `t` is the time of **this attempt**: a retry is signed afresh, so a receiver can enforce a short tolerance. Receivers must reject a request whose `t` differs from their clock by more than **five minutes** (the documented tolerance; our own reference verifier uses the same constant). That bounds a replay of a captured request to five minutes, within which the delivery id lets them recognise it.
- The header is a list of `key=value` pairs separated by commas and carries one `v1` per active secret (two during a rotation overlap) and may later carry a `v2` (a scheme change); receivers accept the request if any `v1` matches and ignore unknown keys. Verification uses a constant-time comparison.
- The body is the **core event** serialized as JSON: `{"id", "type", "version", "org_id", "occurred_at", "ids": {"<thing>_id": "<uuid>"}}`. Ids only. `version` is the event schema version; additive changes keep it, breaking ones bump it.
- Delivery is at-least-once: the job is unique per (event, endpoint) so an event is never queued twice, and a failed attempt is retried with exponential backoff (30 s doubling, capped at 4 h, eight attempts by default). Receivers answer 2xx to acknowledge; they should answer quickly and process asynchronously.
- The sender is hardened against being used as an SSRF proxy: https only, the host is resolved and **every** address must be public (loopback, private, link-local including cloud metadata, carrier-grade NAT, multicast and documentation ranges are refused, IPv4-mapped and well-known NAT64 forms included, and 6to4, Teredo, IPv4-compatible, IPv4-translated and local-use NAT64 addresses refused outright), the check is repeated at connect time on the address actually dialled (so DNS rebinding cannot swap it), redirects are never followed, proxies from the environment are ignored, the whole request is capped at 10 s and at most 1 MiB of the response is read. Operators of self-hosted installs whose receivers live on the LAN list the ranges explicitly in `OPENBEKCI_WEBHOOK_ALLOWED_CIDRS`; nothing private is reachable by default.

## Consequences

- A receiver that can compute an HMAC can verify us; `docs/integrations.md` has Go and Node examples. There is no public key to publish or rotate.
- The shared secret means a receiver that leaks it lets others forge events for that endpoint. The blast radius is one endpoint (secrets are per endpoint) and the events are ids only. Rotating the secret (or deleting and re-creating the endpoint) replaces it; rotate twice to end an overlap early.
- Because the server must read the secret to sign, a compromise of the database **and** `ENCRYPTION_KEY` exposes the secrets. This is the same exposure as every other sealed provider credential (backend §16) and is covered by the same key handling and backup rules.
- Signing with the attempt time means two attempts of one delivery have different signatures but the same delivery id and body.
- Clock skew between instance and receiver beyond five minutes makes valid deliveries fail verification; the documentation tells receivers to run NTP, and the tolerance is symmetric.
- Revisit (a new ADR, a `v2` entry in the header) if receivers need non-repudiation or if per-instance public keys become desirable for the hosted offer.
